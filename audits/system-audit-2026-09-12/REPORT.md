# Life OS — аудит системы, 12 сентября 2026

Аудируемая версия: `32b29af` **и существовавшие на начало аудита незакоммиченные изменения**, включая миграцию `20260911000003_batch_atomic_upsert.sql`. Проверялось фактическое рабочее дерево. Снимок состава и начального git status: [snapshot.json](evidence/snapshot.json); SHA-256 443 файлов исходников/конфигурации: [source-sha256.json](evidence/source-sha256.json).

## Вердикт

**Нет, весь заявленный функционал не реализован. Нет, все функции не работают корректно. Выпуск с реальными пользовательскими данными сейчас заблокирован конкретными дефектами безопасности и сохранности данных.**

При этом приложение действительно существует и выполняет полезные операции: локальные дневники, ручной ввод, поиск еды, OCR, упражнения и подходы, сон, анализы, эксперименты, синхронизация, виджеты и companion для Watch. Оно собирается, и значительная часть штатных проверок проходит.

Главная проблема — корректность переходов между этими частями. Запись может успешно сохраниться с неправильной датой или пищевой ценностью; изменение эксперимента меняет соблюдение протокола; восстановление архива может сообщить успех без восстановления истории. Есть воспроизведённые нарушения серверных границ доступа. Поэтому **«много реализовано» сейчас не означает «можно доверять приложению»**.

Как тестовую сборку для знакомства со сценариями использовать можно. Как единственное хранилище личной истории или надёжного помощника по рекомендациям — пока нет. Потенциальная польза единого дневника понятна; фактическая ежедневная польза, точность распознавания и качество персональных рекомендаций не подтверждены пользовательским пилотом.

## Как проводилась проверка

- Сопоставлены master spec, PRD, функциональная матрица, acceptance criteria, текущий код и прежние отчёты.
- Проверены цепочки UI → модель → локальная база → outbox → API → повторное чтение, особенно коррекция записей, смена identity, отключение разрешений и удаление.
- Выполнены свежие сборки/тесты, чистые миграции, серверные интеграционные проверки и дополнительные проверки обнаруженных дефектов.
- Разделены доказательства: **воспроизведено на реальной локальной БД**, **выполнен настоящий обработчик с подменёнными сетевыми зависимостями**, **проверено по исходникам**, **нужна внешняя проверка**.

Инвентаризация: 130 Swift-файлов основного iOS-приложения (~95,7 тыс. строк, включая вспомогательные test hooks), 62 файла unit-тестов, 23 SQL-миграции, 39 Deno test-файлов. Это **не заявление о равномерном построчном анализе каждой строки**. Глубокая проверка сосредоточена на всех основных функциональных областях и наиболее рискованных межмодульных сценариях. Неизвестных дефектов может быть больше.

Production-код не исправлялся. Созданы отчёты и воспроизводимые проверочные артефакты. Внешние аккаунты не удалялись; SQL-эксперименты выполнялись на локальных временных данных и откатывались. После аудита тестовый Supabase остановлен, три созданных симулятора удалены, исходный tracked diff совпадает побайтно: [cleanup.json](evidence/cleanup.json).

## Самые существенные дефекты и порядок исправления

В профильных отчётах используется `BLOCKER` для требования исправить дефект до выпуска соответствующей функции. Ниже — общая продуктовая очередность: **P0** — прежде любых внешних испытаний; **P1** — до использования как надёжного личного журнала; **P2** — оставшаяся корректность, полнота и UX. Уровень серьёзности не подменяет степень доказанности.

### P0 — серверная граница удаления аккаунтов

**Аутентифицированный пользователь может поставить своей строке задания чужой Auth ID.** Реальная PostgreSQL-проба прошла под ролью `authenticated`: вставка и изменение служебного state разрешены, worker identity не совпадает с владельцем строки. Worker затем доверяет этому Auth ID при вызове Admin deletion. Требуется знание чужого UUID; знание идентификатора не должно давать право удаления. Само чужое удаление в аудите не выполнялось.

Причина — сочетание оставшихся permissive RLS policies, клиентских write grants и отсутствия проверки identity на worker. Одного исправления опечатки в имени policy недостаточно. См. [backend CR-01](backend-review.md), [SQL-доказательство](evidence/deletion-job-authorization.log).

### P2 — полноценное ежедневное использование

- Календарь питания и сна не поворачивает названия дней для Monday-first: 1 сентября 2026, вторник, оказывается под «Пн». Вычисление воспроизведено через Foundation. Features CR-F09.
- Завершённый эксперимент остаётся в Active, пока другие экраны вычисляют уже completed. Features CR-F10.
- Сохранённый анализ нельзя полноценно исправить/удалить; ошибочный приём БАДа нельзя отменить, дозу/схему элемента стека нельзя нормально изменить. Features WR-F01/02.
- OCR анализа не сохраняет resumable draft при уходе с экрана/завершении приложения. Features WR-F03.
- Wellness пишет `mental_health_resources_shown=true` без фактического показа; четыре вопроса PSS-4 отсутствуют. Это незавершённое функциональное обязательство и неверная запись события. Features CR-F12.
- Отложенное Watch-действие получает день доставки и текущего пользователя, поскольку payload не сохраняет время/owner нажатия. Data CR-DI-07.
- Push-unregister ставится в очередь перед sign-out, но после удаления сессии очередь не отправляется. Подтверждённая возможность доставки со старого account token относится, например, к уведомлению, инициированному с другого ещё авторизованного устройства; автономный серверный scheduler в аудите не обнаружен. Data CR-DI-08.
- Попытка стирания оставляет backup actor выключенным до перезапуска даже после ошибки/нового профиля. Data WR-DI-01.
- Первый русский экран сразу запрашивает геопозицию с английским пояснением; баннер о не обновившемся здоровье перекрывает заголовок ещё до HealthKit setup, длинные описания обрезаются. Это наблюдалось в обычном запуске, без тестовых подстановок: [CR-U02/U03 и screenshots](onboarding-review.md).

## Рекомендации: отдельная проблема достоверности

Это не только отсутствие доказанного пользовательского эффекта. Найдены ошибки, которые можно проверить непосредственно.

**CR-R01 — направление изменения перепутано.** При истории 20 и сегодняшнем показателе 40 система пишет «на 20 пунктов ниже». При истории 90 и сегодняшнем 80 — «на 10 пунктов выше». Знак разницы отбрасывается, а текст выбирается по абсолютной зоне текущего значения. Ошибка повторяется в локальном `DailyInsightsService.swift:390` и серверном `_shared/daily_insights.ts:244`. Два теста действующего серверного генератора воспроизвели её.

**CR-R02 — ответ AI принимается без проверки внутренней согласованности.** Настоящий predict handler при подменённом ответе модели `[10,20] + optimal + confidence=1` вернул показатель 15, зону optimal и уверенность 100%, хотя исторических совпадений было 0. Ответ `[-50,-20]` превратился в диапазон `[0,-20]` и score -10. Это тест устойчивости к некорректному upstream output, а не утверждение, что реальный провайдер всегда отвечает так. Сервер ограничивает только одну сторону каждого конца диапазона и доверяет любому допустимому имени зоны; клиент также принимает переданную зону.

Файлы: `supabase/functions/api/insights/predict/index.ts:442`, `:459`, `:471`; `ios/LifeOS/Modules/Shared/Models/PredictiveModels.swift:73`. Необходимо нормализовать оба конца диапазона, выводить зону из итогового score и ограничивать заявленную уверенность фактическим качеством данных. Текст «уверенность 100%» не должен быть просто числом, выбранным LLM.

Воспроизводимые проверки: [recommendation-probes.ts](probes/recommendation-probes.ts), [фактический вывод и четыре упавших assertions](evidence/recommendation-probes.log).

Детерминированные daily insights также формируют тексты на английском непосредственно в коде. Полноценное русское окружение не покрывается EN-only UI-прогоном. Клиническая или статистическая калибровка recovery/what-if не установлена этим аудитом; наличие формул, references и `confidence` само по себе её не доказывает.

## Почему прежние зелёные отчёты не отвечают на вопрос о готовности

Часть прежних проблем действительно исправлена: текущий код компилируется, чистая БД разворачивается, meal/workout detail cache защищает pending edits, Labs умеет дату и дубликаты, единый дневник получил месячную сетку, эксперименты используют описательные сравнения фаз и проверки единиц/adherence. Эти закрытые проблемы не повторены как новые.

Но общие тесты не проверяли найденные комбинации. Например, security script прошёл, а реальный RLS probe допустил чужой Auth ID; тест длительности тренировки прямо ожидает эвристические 15 минут; большинство UI-сценариев запускаются с подготовленными локальными данными и отключённой background work. В онбординге `UITestBootstrap.isEnabled` прямо завершает photo quick win без фото и сохранения. Пройденный экран не доказывает успешное многодневное восстановление/синхронизацию.

Функциональная матрица смешивает статусы «описано» и «реализовано», содержит устаревшие утверждения об отсутствии P1 и ссылается на старый snapshot. Master spec относит некоторые уже существующие поверхности к out-of-scope UI. Поэтому процент «готовности всей системы» из этих документов считать некорректно: сначала нужна актуальная матрица критериев с доказательствами.

## Можно ли получить практическую пользу

**Наиболее реалистичная ценность — единый журнал еды, сна, подходов, самочувствия и анализов с простым исправлением ошибок и сохранной историей.** Для этого необязательны сложные AI-прогнозы. Однако именно исправление и сохранность сейчас содержат препятствия: это непосредственно снижает полезность, а не только качество кода.

Рекомендуемый порядок доведения:

1. Закрыть operational RLS и проверку владельца; добавить негативные проверки настоящей authenticated роли.
2. Довести жизненный цикл данных: восстановление архива, reconnect ownership, удаление/отмена/возобновление, HealthKit tombstones, уведомления и файлы после erasure.
3. Сделать фото необязательным при первом запуске. Исправить повседневные записи: дата/порции/AI-review еды, фактическое время тренировки, расписания и undo БАДов, коррекция анализов и экспериментов.
4. Либо завершить программы тренировок/PSS-4/адаптацию, либо убрать обещания завершённого результата из UI и матрицы. Нормализовать и проверять рекомендации.
5. Пройти чистую установленную сборку, физический iPhone/Watch, live провайдеры и небольшой пилот обычного использования.

Критерии пилота должны измерять поведение: время записи обычной еды; возможность исправить ошибку без дубликатов/потерь; сохранность после app kill, офлайна, reconnect и восстановления; совпадение OCR с оригиналом; понятность и долю ошибочных рекомендаций; продолжение использования. В рамках аудита пилот не проводился, его результаты в проверенных материалах не найдены. Поэтому утверждать «приложение будет приносить пользу» как установленный факт нельзя.
